# 03 — Long-lived MicroVM

The one case where a `Microvm` custom resource is the right tool.

Everything else in these examples pushes MicroVM creation towards application
code. This example is the exception: a **single, named, platform-owned MicroVM**
that should exist continuously. A shared development box, a pinned demo
environment, a staging instance. Something a human refers to by name.

## Files

| File | Purpose |
| --- | --- |
| [`microvm.yaml`](microvm.yaml) | One long-lived MicroVM with an idle policy |

## Prerequisites

- [`../01-platform-quickstart/`](../01-platform-quickstart/) applied, with
  `quickstart-image` in state `CREATED`.
- The execution role from
  [`../02-developer-handoff/execution-role.yaml`](../02-developer-handoff/execution-role.yaml).

Both are referenced by Kubernetes name rather than ARN, so no ARNs appear in
`microvm.yaml`.

## Steps

```bash
kubectl apply -f microvm.yaml

kubectl get microvm shared-dev-box \
  -o custom-columns='NAME:.metadata.name,MICROVM-ID:.status.microvmID,STATE:.status.state' \
  --watch
```

```
NAME             MICROVM-ID                                    STATE
shared-dev-box   <none>                                        <none>
shared-dev-box   mvm-01234567-abcd-ef01-2345-6789abcdef01      PENDING
shared-dev-box   mvm-01234567-abcd-ef01-2345-6789abcdef01      RUNNING
```

The controller reports the resource synced once `state` is `RUNNING` or
`SUSPENDED`:

```bash
kubectl wait --for=condition=ACK.ResourceSynced microvm/shared-dev-box --timeout=10m
```

Connect to it the same way as any other MicroVM — the endpoint needs an auth
token, which is not a custom resource:

```bash
MICROVM_ID=$(kubectl get microvm shared-dev-box -o jsonpath='{.status.microvmID}')
ENDPOINT=$(kubectl get microvm shared-dev-box -o jsonpath='{.status.endpoint}')

TOKEN=$(aws lambda-microvms create-microvm-auth-token \
  --microvm-identifier "$MICROVM_ID" \
  --expiration-in-minutes 30 \
  --allowed-ports '[{"allPorts":{}}]' \
  --query authToken --output text)

curl "https://$ENDPOINT/" -H "X-aws-proxy-auth: $TOKEN"
```

## Suspend and resume

`idlePolicy` in this manifest suspends the MicroVM after 15 minutes without
inbound traffic and resumes it automatically when a request arrives. Memory and
disk state survive suspension, so a developer returning to the box finds it as
they left it, and you stop paying the running rate while it sits idle.

`SUSPENDED` counts as synced, so a suspended MicroVM is not an error state and
`kubectl wait` will not hang on it.

To suspend or resume on demand, call the API. There is no spec field:

```bash
aws lambda-microvms suspend-microvm --microvm-identifier "$MICROVM_ID"
aws lambda-microvms resume-microvm  --microvm-identifier "$MICROVM_ID"
```

The controller will observe the new state on its next reconcile and update
`status.state`. It will not fight you — suspension is not drift.

## Editing this resource produces a terminal error

`Microvm` has no update operation. Every spec field is compared during
reconciliation, and the update path returns `NotImplemented`, so changing
anything — even a single number in `idlePolicy` — puts the resource into a
terminal error state:

```bash
kubectl patch microvm shared-dev-box --type=merge \
  -p '{"spec":{"idlePolicy":{"maxIdleDurationSeconds":600}}}'

kubectl get microvm shared-dev-box -o jsonpath='{.status.conditions}' | jq
```

```json
[
  {
    "type": "ACK.Terminal",
    "status": "True",
    "message": "NotImplemented"
  }
]
```

The MicroVM keeps running with its original configuration. To change it, delete
the resource and create a new one. Because `RunMicrovm` is a create-only
operation, there is nothing the controller could do in place.

This is worth internalising before you build automation around `Microvm` CRs: they
are immutable, and a config change means a new MicroVM.

## Why this does not scale to one MicroVM per session

It is tempting to generalise this example — a `Microvm` per user, generated by a
templating layer. Don't. The reasons are structural, not stylistic:

| | Long-lived MicroVM (this example) | Per-session MicroVM |
| --- | --- | --- |
| Count | A handful, named by humans | Thousands, named by machines |
| Lifetime | Days to weeks | Seconds to minutes |
| Created by | A reviewed commit | A request handler |
| Needs to exist within | Whenever someone gets round to it | Milliseconds |

Concretely, per-session `Microvm` CRs break down because:

- **The resync period is ten hours.** A five-minute session is created and
  deleted without the controller ever reconciling it a second time. You get none
  of the benefit of a reconciler while paying its full latency cost.
- **Creation latency is not `RunMicrovm` latency.** It is `RunMicrovm` plus
  work-queue scheduling. The chart ships `defaultMaxConcurrentSyncs: 1`, so a
  burst of sessions is processed serially by default.
- **etcd is not a session store.** One object per session, each carrying status
  and conditions, all watched by the controller.
- **Leaks cost money.** If a CR is orphaned, the MicroVM runs until
  `maximumDurationInSeconds` expires. Application code can terminate in a
  `finally` block; a leaked custom resource cannot.
- **Immutability becomes a trap.** Any per-session configuration change means
  delete and recreate, which for a session-scoped resource means losing the
  session.

For per-session MicroVMs, call `RunMicrovm` from application code — see
[`../02-developer-handoff/`](../02-developer-handoff/), and
[When not to reach for a custom resource](../../README.md#when-not-to-reach-for-a-custom-resource)
in the repository README.

## Cleaning up

`microvm.yaml` sets `services.k8s.aws/deletion-policy: retain`, which is
appropriate for long-lived infrastructure but means `kubectl delete` leaves the
MicroVM running and billing:

```bash
kubectl delete -f microvm.yaml

# The AWS resource is still there. Terminate it explicitly.
aws lambda-microvms terminate-microvm --microvm-identifier "$MICROVM_ID"
```

Remove the annotation if you would rather deletion propagate. The retain policy
is a deliberate choice here, so that an accidental `kubectl delete` does not
destroy a shared environment someone is working in.
